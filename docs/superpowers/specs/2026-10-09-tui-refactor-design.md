# 服务端 TUI 改造 设计文档

**日期：** 2026-10-09
**状态：** 待评审
**范围：** `src/server/`（CLI 代理服务器）表现层改造

---

## 1. 目标

把代理服务器终端的输出从「二维码打印一次就被日志顶出屏幕」改成 TUI 布局：**二维码常驻固定头部，日志在下方滚动**。

**背景与动机。** 这个终端是开发者排障「模拟器调用有没有转发到真机」的唯一窗口——链路是 `模拟器(开发者工具) ←→ 代理服务器(本终端) ←→ 真机小程序`。当前每秒数条的 `转发调用 / 转发响应 / 推送事件` 日志会在几秒内把二维码顶走，导致两个问题：真机需要重连时扫不到码；出问题时日志也已经滚走。这两个问题同源。

**成功标准：**

1. 二维码在会话期间始终可见（终端足够高时）
2. 日志持续滚动且可回溯（不因滚走而丢失）
3. `dist/server.js` 仍然是零运行时依赖的单文件产物
4. 非 TTY 场景（重定向、CI）行为与改造前完全一致

---

## 2. 范围与约束

### 在范围内

`src/server/index.ts`、`src/server/server.ts`、`src/server/utils.ts`，新增 `src/server/tui.ts`。

### 明确不在范围内

- **`src/index.ts` 完全不动。** 它是小程序端库，`console.log` 进的是支付宝 IDE 控制台，不存在 TUI 的载体。
- **不改二维码载荷格式。** `xlmpaas://<appId>?url=<encoded>` 是 `miniapp/utils/urlParser.js` 的契约，缩短载荷虽能显著压缩二维码行数，但要同步改真机小程序，超出本次范围。
- **不做日志区翻页/搜索。** 已明确排除：只做自动滚动 + 可选落盘。
- **不引入任何运行时或开发时依赖。** 手写 ANSI。
- **不加测试设施。** 项目当前无 test 脚本、devDeps 无 vitest/jest，本次不新增。

### 硬约束

**零依赖产物。** `rollup.config.mjs` 要求 `dist/server.js` 自包含（ws / qrcode-terminal / minimist 全部打入，仅 `bufferutil`、`utf-8-validate` 保持 external），当前 77KB。这是排除 ink（React + yoga WASM，且 v4+ 是 ESM-only，与 CJS 产物冲突）和 terminal-kit 的根本原因。

## 3. 终端行数预算（本设计的核心约束）

实测 `qrcode-terminal` 在 `{ small: true }` 下、当前载荷（60 字符）的输出：

| 载荷长度 | 二维码行数 |
|---|---|
| 32 字符 | 14 行 |
| 60 字符（当前） | **18 行** |
| 106 字符 | 20 行 |

展开态头部固定开销 = 分隔线 1 + 标题 1 + URL 1 + 状态 1 + 分隔线 1 = **5 行**，故展开态头部共 **23 行**。

**结论：在 80×24 终端上钉住完整二维码后日志区一行不剩，布局不成立。** 这是物理约束，非实现问题。实测当前 shell pty 即为 80×24。

因此采用**自适应 + 切换键**策略：

- **rows ≥ 28**（18 QR + 5 开销 + 5 行最小日志区）：默认展开二维码并常驻
- **rows < 28**：默认收起，头部收敛为 3 行（标题 / URL / 状态），末行提示 `按 q 显示二维码`
- 两种状态下 `q` 均可就地展开/收起二维码

**副产品：确定不需要显示宽度计算。** 因为既不截断日志行（超宽由终端自动折行，区域内折行不影响滚动数学），也不画竖线边框（分隔线用 `─` 重复 `columns` 次即可）。这恰好绕开了手写 ANSI 里最容易出错的部分——中文与 ✅⚠️ 这类 emoji 的宽度。经实测，`qrcode-terminal` 的输出是**纯文本块字符、不含任何 ANSI 转义**，同样无需处理。

## 4. 渲染机制

alt screen + 滚动区域，让终端自己滚动，不维护日志缓冲区。

```
进入    \x1b[?1049h                     切到备用屏幕
        \x1b[2J\x1b[H                   清屏归位
        画头部（rows 1..H_head）
        \x1b[{H_head+1};{rows}r         把下方剩余区域设为滚动区
        \x1b[{H_head+1};1H              光标落到日志区顶部
日志    write(line + '\n')               终端在区域内自行滚动，头部不受影响
状态    \x1b7 → \x1b[{row};1H\x1b[2K写 → \x1b8    保存/恢复光标，只重画那一行
q 切换  整屏重绘（清屏 → 新头部 → 重设滚动区 → 回填最近 N 行）
resize  同上，走同一条重绘路径
退出    \x1b[r → \x1b[?1049l             复位滚动区、回主屏，再打印一次 URL + 二维码
```

`q` 切换与 resize **共用同一条重绘路径**，因此需要一个固定容量的环形缓冲（**上限 200 行**，与可见高度无关）保存历史日志用于回填。回填时取其中最后 N 行（N = 当前日志区高度）。

容量之所以不取「日志区高度」：终端从 80×24 拉高到 80×50 时，新增的行需要从历史里回填，若缓冲只按旧高度存就会留下一片空白。200 行是「够覆盖任意常见 resize」与「内存占用可忽略」之间的取值。

这是重绘所需的回填缓冲，**不是**可翻页的缓冲区——翻页已在范围外。

**选择 alt screen 而非「普通缓冲 + 滚动区」的理由：** 后者虽然退出后头部仍留在 scrollback 里，但滚动区内的行滚出后同样会丢失（不会进 scrollback），且 resize 后头部锚点位置在普通缓冲里难以重建。alt screen 下整屏归我们所有，重绘是平凡的。退出时二维码丢失的问题由「退出钩子重打印一次」补偿。

## 5. 模块改动

| 文件 | 改动 |
|---|---|
| `src/server/tui.ts` | **新增**，约 200 行。接口：`isSupported()`、`enter()`、`renderHeader(info)`、`setStatus(text)`、`appendLog(line)`、`toggleQr()`、`exit()` |
| `src/server/utils.ts` | `Utils.log()` **签名不变、5 个调用点一行不动**；内部改为委托可替换 sink（`Utils.setLogSink()`，默认仍是 `console.log`）。新增 `Utils.formatLogLine(message, type)`，供 TUI 与日志文件共用同一份格式化实现 |
| `src/server/server.ts` | `displayConnectionInfo()` 拆为 `renderTuiHeader()` 与 `printPlainHeader()`（后者保留现有框线 + 二维码）；状态行数据取自**已存在的** `deviceManager.getAllDevices()`（`device-manager.ts:97`），1 秒轮询、仅在结果变化时重绘 |
| `src/server/index.ts` | 解析 `--no-tui`、`--log-file <path>`；决定运行模式；接线生命周期与信号处理 |
| `rollup.config.mjs` | **预期不改**。若新增文件的打包触发问题再单独评估 |

### 设备状态用轮询而非回调

`getAllDevices()` 已存在且返回的正好是状态行所需的数据（`deviceId` / `hasMiniapp` / `lastHeartbeat`），1 秒一次的轮询开销可忽略。为此给 `DeviceManager` 增加事件回调机制属于不必要的耦合与改动面扩张。

### 日志文件

`--log-file <path>`，默认关闭。开启后每行格式化日志同时写入该文件（复用 `Utils.formatLogLine`，与终端显示内容一致）。用一次性创建的 write stream 追加写入，而非每行 `appendFileSync`。

## 6. 边界情况

1. **非 TTY。** `!process.stdout.isTTY` → 完全不进 TUI，走改造前的纯日志路径。**这条是必需的**，否则 `npm start > log.txt` 会被 ANSI 序列污染。`--no-tui` 可强制关闭。
2. **终端恢复。** SIGINT / SIGTERM / `uncaughtException` / `process.on('exit')` 四条路径**都必须**执行 `exit()`，否则终端会被留在 alt screen + raw mode 里。这是此类改动最典型的翻车方式，需重点验证。
3. **raw mode 下 Ctrl+C 不再产生 SIGINT**，需自行接 `\x03` 并走同一条关闭路径；`q` 切换二维码；其余按键忽略。
4. **日志行超宽**：不截断，由终端自动折行。
5. **状态行重绘的安全性**：状态行位于滚动区**上方**，用 `\x1b7`/`\x1b8` 保存恢复光标后移动过去重绘，不会触发滚动区滚动。日志写入与状态重绘都是同步写，不会交错。

## 7. 验证方式

无自动化测试设施，故以命令 + 手动验证为准：

- `npm run type-check`
- `npm run build`，并确认 `dist/server.js` 仍为零依赖单文件、体积量级未变（当前 77KB）
- 手动清单：
  1. `npm start` → 观察布局、状态行随设备上下线更新
  2. `npm start | cat` → 确认非 TTY 降级，输出无 ANSI 污染
  3. 拖动窗口 resize → 确认重绘正确、二维码与日志区比例合理
  4. 在 80×24 与高终端两种尺寸下分别启动，确认自适应阈值生效
  5. 按 `q` → 确认二维码展开/收起
  6. Ctrl+C → 确认终端恢复正常、主屏留有 URL + 二维码
  7. 强制抛异常 → 确认终端同样被正确恢复

## 8. 已识别但不在本次处理的既有问题

- **`Utils.getLocalIP()` 取第一个非内部 IPv4 网卡。** macOS 多网卡（VPN、Docker bridge、多个 Wi-Fi）下可能取到错误的地址——此时二维码钉得再牢也没用，真机扫到的地址连不上。这是既有行为，TUI 改造既没有引入也没有加剧它。**建议单独立项处理**，本次仅在实现时留意不要让它更难排查。
- **`src/server/server.ts:105` 用的是导入的 `config.appId`，而非 `this.config` 上的配置。** 属于既有小瑕疵。实现时应保证 TUI 头部与纯文本头部使用**同一个** appId 来源，避免两条路径生成不同二维码。

## 9. 设计决策记录

设计阶段由用户逐项确认的决策，作为实现时的依据：

1. **实现方式：手写 ANSI，零依赖。** 排除 terminal-kit 与 ink（理由见 §2 硬约束）
2. **日志区能力：自动滚动 + 可选落盘。** 已在 §5 体现为 `--log-file`；排除内置可翻页缓冲区
3. **头部内容：二维码 + URL + 一行实时状态。** 排除逐行列出 deviceId
4. **矮终端策略：自适应 + `q` 切换。** 见 §3；排除「强制常驻」与「整个退回纯日志」
5. **改动范围限于 §5 表格中的 4 个文件**
6. **设备状态用轮询**，不给 `DeviceManager` 加回调
7. **不新增测试设施**
